# Skill 寫作判準

適用於 `.claude/skills/**` 的所有 skill。新增或修改 skill 時遵守本檔。

## 出處與樣本限制

本判準逆推自一份外部教材（TibaMe「Claude AI 驅動全端開發工作流」）對 10 個 skill 的分析。
**樣本只有一位作者的 10 個 skill，且集中在「內容生產」與「git 工作流」兩類；
資料處理、資安掃描、跨系統整合沒有樣本。** 本 Starter 現有的 skill 恰好都落在
git 工作流那一類，遷移性因此算高 —— 但不要把它當成普世規範，
遇到樣本外的 skill 類型時，判準本身也應被檢討。

## 先問：這該不該是一個 skill

**只有規則、沒有流程的東西不要做成 skill。** 一段「命名要用 kebab-case」屬於規則，
寫進 `CLAUDE.md` 或 `AGENTS.md` 即可；skill 的價值在於把一段**多步驟、有前提、
有判斷、有輸出格式**的作業固化成可重複的 SOP。若你的 SKILL.md 寫完只有幾條條列，
它多半應該是一段規範而不是一個 skill —— 你付了 token，卻沒換到 SOP 的確定性。

## 七段骨架

一個合格的 SKILL.md 依序包含：

1. **frontmatter** —— `name` 與 `description`。`description` 必須寫出**實際會講出口的觸發詞**，
   不只是抽象情境。句型：「當使用者提到『X』、『Y』、『Z』時觸發」。
2. **`## 前置檢查`** —— **STEP 1 永遠是確認前提成立，不是開始做事。**
   列出必須成立的條件，以及每個條件不成立時**要停下來說什麼**。
3. **`## 規則`** —— 表格。一列一條，欄位至少含「規則」與「理由」。
4. **`## 範例`** —— 表格，且**必須有「判斷依據」欄**。只給輸入輸出而不說為什麼，
   AI 會學到表面樣式而不是判準。
5. **`## 確認關卡`** —— 任何不可逆操作之前：列出提案、寫死輸出長相、等使用者點頭。
   沒有不可逆操作的 skill 可省略本節，但要在前置檢查註明「本 skill 不做任何寫入」。
6. **`## 邊界情況處理`** —— **這是整份 SKILL.md 最值錢的一節。**
   它的功能是把 AI 會亂猜的地方一條一條堵住。至少三條，每條寫「情況 → 該怎麼做」。
7. **`references/`**（選用）—— 模板、長表格、範例集放這裡，主文保持精簡。
   模板檔用 HTML 註解承載規則（渲染時看不到、AI 讀得到、規則與版型同檔不會走鐘），
   並在主文明寫「模板是唯一事實來源」與「產出不保留註解」。

## 邊界節怎麼長出來

不要一次想齊。**skill 每被使用一次，它做錯的地方就是一條該補進邊界節的規則。**
這是唯一有效的方法：邊界情況來自實際失敗，不來自事前想像。

## 本 Starter 的額外要求

這三條優先於上面任何一條：

- **skill 不得成為第二套產品 Spec。** 產品意圖、可觀察行為、acceptance criteria
  由 OpenSpec 獨占（見 `AGENTS.md`〈與其他 Agent 框架的邊界〉）。
- **skill 不得宣稱 gate 已通過。** 沒有 evidence 就不要說通過；
  evidence 的擁有權在 `verify.sh` 與 `workflow/evidence/`，不在 skill。
- **skill 不得繞過 Control Plane。** 需要改 `workflow/STATE.md` 就走
  `workflow_transition.py`；hook 拒絕時修正操作範圍，不要繞過。

## 一頁自檢清單

送出前逐項確認：

- [ ] `description` 含實際觸發詞，不只抽象情境
- [ ] STEP 1 是前置檢查，且寫明「不成立時停下來說什麼」
- [ ] 規則表存在
- [ ] 範例表存在，且有「判斷依據」欄
- [ ] 不可逆操作前有確認關卡，且寫死了輸出長相
- [ ] `## 邊界情況處理` 至少三條，每條是「情況 → 該怎麼做」
- [ ] 沒有建立第二套產品 Spec
- [ ] 沒有在缺 evidence 時宣稱通過
- [ ] 長模板／長表格已移入 `references/`
